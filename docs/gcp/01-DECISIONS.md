# GCP — decisions

Every choice that shapes M11 (GCP support), in the same shape as the repo-root
`DECISIONS.md`: *the question we faced · the options we had · what we chose ·
why · where it shows in the code*. G1–G6 were settled before this round opened
and are recorded, not re-argued. G7–G21 come from reading the engine against
real `google_*` fixtures; each one names the file and line that forces it.

Reading tips: `path:line` points into this repo and has been checked against the
file. "IR" = the dataclasses in `iacsim/core/models.py`. A "hop" is one step of a
request. `TYPE_MAP` means the table at `iacsim/graph/normalisers/aws.py:41` and
its GCP twin, specified in `02-TYPE-MAP.md`.

An explicit `provider:` in `iacsim.yaml` still wins. A mixed directory warns and names what was dropped.** | Zero config is the same promise Q3 and D10 already make; a user who runs `iacsim run ./terraform` on a GCP repo must not get an empty graph. Keeping them honest costs a hop-count difference instead. **Known cost, recorded on purpose: `iacsim diff` between an AWS stack and a GCP stack is no longer hop-comparable — totals stay honest, hop counts do not.** | `02-TYPE-MAP.md` "the 0 ms chain", G9 below |
| **G4** | Six engine files hardcode AWS subtype names. The AWS tables move out of `processing.py` / `cold_start.py` into `AwsNormaliser` UNCHANGED.** | Byte-identical AWS behaviour is the acceptance test, and the existing 290 tests are the regression proof. A plugin is impossible *today* precisely because these tables are not plugin-extensible — G4 is what would make it possible. | `iacsim/latency/rules/processing.py:37-43`, `iacsim/latency/rules/cold_start.py:21`, `iacsim/simulator/capacity.py:36`, `iacsim/analyzer/saturation.py:144-159`, `iacsim/simulator/walkers/load.py:196-203`, `iacsim/latency/calibrate/calibrator.py:33-34` |

| **G6** | Does GCP capacity modelling (`--walker load`) land in round 1? | Model capacity now · **defer to a later work package** | **Deferred. Round 1 = graph + timings + diff.** | `_resource()` already returns `None` for any subtype it does not know, so the load walker degrades quietly instead of crashing, and `simulator/` and `analyzer/` stay untouched this round — which is what the Phase 3 rule in `TIMELINE.md` ("only new registrations", currently line 544) asks for. | `iacsim/simulator/capacity.py:161` (`return None`), `iacsim/simulator/capacity.py:111-117` (`resource_of`) |

## 2. Correctness bugs GCP exposes (G7–G9)

These are not missing features. Each one makes iacsim print a confident wrong
number today, and each is triggered by input the tool accepts without error.

| id | The question | Options we had | What we chose | Why | In code |
|---|---|---|---|---|---|
| **G7** | Every non-`aws` provider block is skipped, so a `provider "google" { region = … }` is ignored and every GCP node gets `region=None`. | Leave it and require `--region` · special-case `google` next to `aws` · **key the region map by provider name** | **Generalise `_resolve_regions` to be keyed by provider name; derive a resource's default provider from its type prefix (`google_compute_instance` → `google`) instead of hardcoding `"aws"`. `google-beta` resolves to the same provider as `google`.** | The failure is silent, not loud: `region=None` on both sides makes the distance rule fall through to `same_region_unknown_az` (0.5 ms), so a `us-central1` → `europe-west1` call reads as nearly free instead of ~100 ms. That destroys the tool's headline claim on the first GCP repo it sees. `google-beta` is not an edge case — real fixtures set `provider = google-beta` on every resource. | the bug: `iacsim/parsers/terraform/loader.py:167` (`if block["name"] != "aws": continue`), `loader.py:160-165`, `loader.py:181-183`, `loader.py:348`, `loader.py:438-442` (`_provider_alias` returns `"aws"`); the consequence: `iacsim/latency/rules/distance.py:41`, warned once per node at `distance.py:46-52` |
| **G8** | A subtype missing from `INVOKE_KEY_FOR_SUBTYPE` is charged **nothing** on an INVOKE hop, and the rule returns `{}` rather than raising. | Raise on an unknown subtype · warn · **write the type map and the latency profile as one unit, and test the invariant** | **`TYPE_MAP`, `INVOKE_KEYS` and the `processing.<subtype>` block are written together in one work package, plus a test asserting that no subtype in `TYPE_MAP` lacks a profile entry or an invoke key.** | This is precedent, not theory: `kinesis` sits in `INVOKE_KEY_FOR_SUBTYPE` today with key `publish`, and `defaults.yaml` has no `processing.kinesis` block — so `processing_for()` returns `{}`, `block.get("publish")` is `None`, and every hop into a Kinesis stream is free. Ship 40 GCP subtypes without the invariant and that happens 40 times. Raising is wrong (D20: nothing crashes on unknown input); a test is the right place for the check. | the trap: `iacsim/latency/rules/processing.py:37-43`, `processing.py:57-60` (returns `{}` when `value is None`); the precedent: `iacsim/latency/defaults.yaml:38-80` has no `kinesis:` block |
| **G9** | G3 prices the LB chain's internal hops at 0 ms. Is a `processing` of 0 enough? | Yes, set `processing.<chain subtype>` keys to 0 · **no — suppress distance on the chain too** | **Both: the chain subtypes get `route: 0` in the profile AND the chain hops must not be charged distance.** Recorded as a decision because it needs more than a table entry. | A 5-node chain is 4 internal hops. Each is a ROUTE, which is in `SYNCHRONOUS`, so the walker doubles its distance. With every chain node regional or global (`az` is `None`), the distance rule returns `same_region_unknown_az` = 0.5 ms, doubled = 1.0 ms per hop → ~4 ms of phantom network on every GCP request. Small, but it is exactly the "confident wrong number" G3 set out to avoid, and it grows with the profile's `same_region_unknown_az`. | `iacsim/simulator/traversal.py:75` (`SYNCHRONOUS` includes ROUTE), `traversal.py:283` (`breakdown["distance"] *= 2`), `iacsim/latency/rules/distance.py:40-41`, `iacsim/latency/defaults.yaml:14` |

## 3. The normaliser (G10–G13)

| id | The question | Options we had | What we chose | Why | In code |
|---|---|---|---|---|---|
| **G10** | Where does a GCP node's placement come from? | Copy `aws.py` (provider region first, resource attributes second) · **resource first, provider second** | **`_placement()` reads the resource's own `region` / `zone` / `location` first and falls back to the provider region. GCP `zone` (`us-central1-a`) maps onto the existing `Placement.az`; `network` → `.vpc`; `subnetwork` → `.subnet`. No IR change.** | The emphasis is reversed from AWS on purpose. An AWS resource inherits its region from the provider block and only names an AZ; a GCP resource usually declares its own `region`, `zone` or `location` and the provider block is the fallback. Reading provider-first would overwrite a Cloud Run service pinned to `europe-west1` with the provider's `us-central1`. | the AWS shape being mirrored: `iacsim/graph/normalisers/aws.py:169-188`; the fields: `iacsim/core/models.py:105-110` (`Placement`); consumed at `iacsim/latency/rules/distance.py:33-44` |
| **G11** | GCP subtype names — reuse AWS ones or invent GCP-native ones? | Map Memorystore → `elasticache`, a GCE VM → `ec2` (free numbers, free capacity) · **GCP-native names throughout** | **GCP-native names — `cloud_run`, `spanner`, `pubsub`, `cloud_sql`, `gcs`, `gce`, `memorystore`. Never reuse an AWS subtype name.** One documented exception: `NodeKind.NETWORK` subtypes (`vpc`, `subnet`, `vpc_peering`, `nat`) are shared, because NETWORK nodes have no `processing` block and are never a hop. | `Profile.processing_for` is keyed by the **bare** `node.subtype` — there is no provider field on `Node` at all — so GCP-native names just work with no engine change. The same fact is the trap: naming Memorystore `elasticache` would silently inherit AWS's read/write numbers *and* AWS's capacity behaviour, and nothing would warn. One deliberate prefix survives: GCP's own product is also called API Gateway, so it is `gcp_api_gateway` to avoid colliding with the AWS `api_gateway` block. | `iacsim/core/models.py:310-322` (`processing_for`), `iacsim/core/models.py:122-125` (`Node` has `subtype`, no provider), `iacsim/simulator/capacity.py:120-161` (`_resource` switches on the same bare subtype), `iacsim/scenarios/inferred.py:41` (`NOT_A_HOP`) |
| **G12** | Where do GCP region-pair distances go? `CODE_FLOW.md` promised a `distance.<cloud>` block. | Implement the nested `distance.<cloud>` block the docs promise · **merge GCP pairs into the existing flat `cross_region` map, and correct the doc** | **Merge flat. Then fix `CODE_FLOW.md` — the `distance.<cloud>` block it advertises does not exist in the code.** | The `cross_region` key is a sorted `"a/b"` string, and GCP region names (`us-central1`, `europe-west1`) do not collide with AWS ones (`us-east-1`, `eu-west-1`), so one flat map is unambiguous. It is the zero-code path, and it matches M11's own scope wording in the `TIMELINE.md` M11 row ("inter-region defaults", currently line 539). Implementing the nesting would mean editing `distance.py` and every profile file for no behaviour gained. Correcting the doc is the honest half of the decision. | `iacsim/latency/rules/distance.py:37-39`, `iacsim/latency/defaults.yaml:11-22`, the correction, now written: `CODE_FLOW.md:370-376` ("Adding a cloud provider — one correction and four contracts") |
| **G13** | Entry points: how does a GCP graph get a starting node? | Add a `gcp_internet` node · make the id configurable · **create the same `internet` node with the same id** | **The GCP normaliser MUST add one `NodeKind.EXTERNAL` node with the literal id `internet` and edge it to every GATEWAY / LB / CDN node.** | The literal string `"internet"` is a hardcoded contract in two engine files. Match it and inferred scenarios, entry-point discovery and the `internet_to_edge` charge all work with zero engine change; miss it and a GCP graph infers no scenarios at all, with no error. This is the single cheapest thing the GCP normaliser must get exactly right. | the contract: `iacsim/scenarios/inferred.py:69` (`e.src == "internet"`), `iacsim/simulator/traversal.py:134-135` (`find_edge("internet", …)`); the AWS implementation to copy: `iacsim/graph/normalisers/aws.py:101-102`, `aws.py:131-138`; the consumer: `iacsim/latency/rules/distance.py:30-31` |

## 4. Inference rules (G14–G19)

Four existing rules were read end to end to decide reuse vs rewrite. The answer
differs per rule; "it's all AWS-specific" is not true.

| id | The question | Options we had | What we chose | Why | In code |
|---|---|---|---|---|---|
| **G14** | `env_var` — reuse or rewrite? | Rewrite as `gcp_env_var` · **reuse with a per-provider attribute tuple** | **Reuse. The rule's executable code is provider-neutral; it couples to a cloud through exactly one constant, `CONFIG_ATTRS`. Make that tuple per-provider.** | The only `aws_` string in the file is a docstring example (`env_var.py:6`). Everything else walks placeholders and looks nodes up by address. GCP hides env vars in three places — Cloud Run at `template.spec.containers[].env[]`, Cloud Functions v1 at `environment_variables`, v2 at `service_config.environment_variables` — which is a tuple change plus a container-walker sibling to `_container_env`, not a new rule. | `iacsim/graph/inference/env_var.py:33` (`CONFIG_ATTRS`), `env_var.py:41-63` (no AWS type names), `env_var.py:66-81` (`_container_env`, the shape to mirror for Cloud Run) |
| **G15** | `vpc_peering` — reuse or rewrite? | Rewrite · **generalise** | **Generalise: the rule is 3 AWS references in 27 lines** — the type name and two attribute names. Take them from a per-provider table so `google_compute_network_peering.{network, peer_network}` works through the same code. | Rewriting 27 lines to change 3 strings is how a codebase grows two copies of one idea. | `iacsim/graph/inference/vpc_peering.py:19-21`, whole file is 27 lines |
| **G16** | `iam_policy` — reuse or rewrite? | Generalise the action tables · **rewrite as `gcp_iam_binding`** | **Rewrite.** GCP IAM has a different shape, not different strings. | AWS IAM is a policy document with resource-scoped action lists (`Statement[].Action` + `Statement[].Resource`), and the rule's whole machinery — `_statements`, `_as_list`, `_edge_kinds` verb matching — reads that shape. GCP IAM is a binding: `role = "roles/datastore.user"`, `member = "serviceAccount:…"`, attached to a resource or a project, with no action list and no resource list. The mapping is role → EdgeKind and member → principal; nothing above survives. | the AWS shape: `iacsim/graph/inference/iam_policy.py:60-88`, `iam_policy.py:91-99` (`_statements`), `iam_policy.py:108-121` (`_edge_kinds`); the reusable idea: `iam_policy.py:48-57` (principal → role index) |
| **G17** | `target_group` — reuse or rewrite? | Reuse · **copy the pattern, not the code** | **New `gcp_lb_chain` rule built on `target_group`'s two-dict-join shape** (`{join key → [(lb, evidence)]}` × `{join key → [(target, evidence)]}`, then cross-product into edges). The AWS type names, attribute names and join key are all different; the structure is exactly right. | The GCP chain is 4 joins, not 1, and it mixes reference styles inside one wiring: `google_compute_url_map.default.id`, `…backend_service.default.self_link` and `…target_http_proxy.p.name` all appear (visible in `run/multiple_regions`). `addresses_in()` already strips the attribute, so all three resolve to the same address — the rule must join on the **address**, never on the attribute name. Joining on `.id` alone silently drops half the chain. | the pattern: `iacsim/graph/inference/target_group.py:28-56`, `target_group.py:66-73`; the resolver that makes the three styles equivalent: `iacsim/core/refs.py:36-50` (`split_address`), `refs.py:57-61` (`addresses_in`) |
| **G18** | `inference.rules` is one flat global list. Do GCP rules go in it? | Make the list provider-aware (`inference.rules.<provider>`) · **keep one flat list** | **Keep one flat list. GCP rules run on AWS stacks as no-ops, and vice versa.** | Every rule already starts by looking up its own resource types (`raws_of_type`) or its own node kinds, and returns `[]` when it finds none — an AWS run executing `gcp_lb_chain` is one empty list comprehension. The waste is real and negligible; a provider-aware list adds a config shape, a merge rule and a migration for users who have already pinned `inference.rules` in `iacsim.yaml`. Revisit if the list passes ~20 rules or a rule becomes expensive. | `iacsim/core/config.py:22-31` (the flat list), `iacsim/core/pipeline.py:59-63` (rules are looked up by name and run in order), `iacsim/graph/inference/_common.py:12-13` (`raws_of_type` — the cheap no-op) |
| **G19** | Which new GCP rules are needed? | — | **Five: `gcp_lb_chain`, `gcp_iam_binding`, `gcp_eventarc`, `gcp_pubsub_push`, `gcp_workflows`.** | They cover the five ways a GCP stack states "this talks to that" that no AWS rule can see: the LB chain (G17), IAM bindings (G16), Eventarc triggers (source → trigger → destination), a Pub/Sub subscription's `push_config.push_endpoint` pointing at a Cloud Run URL, and a Workflows YAML source calling services by URL. Each is a registration under `INFERENCE_RULES`, added to the flat list per G18. | the ABC and registry: `iacsim/core/interfaces.py:53-56`, registrations mirroring `iacsim/graph/inference/vpc_peering.py:15-16` |

| **G20** | Cloud Run / Cloud Functions cold start is arguably GCP's most important latency effect. Patching the `if` works once and breaks again at Azure. ## 6. Parked

- **A GCP `MetricSource` for Cloud Monitoring.** `iacsim calibrate` is CloudWatch-only, and `MetricSource.KINDS` (`iacsim/core/interfaces.py:156`) still names AWS subtypes — see G21. Same shape as D31: a registered source plus `calibrate.sources.cloud_monitoring`, no engine change once `KINDS` is per-provider.
- **GCP capacity modelling** (`--walker load`) — G6. Needs `capacity.<subtype>` blocks, `RPS_CAPPED` membership (`iacsim/simulator/capacity.py:36`) and the branches in `_resource` (`capacity.py:120-161`) and `saturation.py:144-159`, all of which G4's tables would carry.
- **Cloud CDN as a subtype switch.** It is `enable_cdn = true` on a backend service, not a resource — so it cannot be a `TYPE_MAP` row. Either a second subtype chosen at normalise time or an attribute the profile reads. Deferred until there is a fixture with it on the request path.
- **Private Service Connect (PSC).** Named in M11's scope (the `TIMELINE.md` M11 row) but it changes *reachability*, not the request shape, and `Placement` has no field for it.
